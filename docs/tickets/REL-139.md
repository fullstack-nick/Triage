# REL-139 — safe local release

Problem: independently correct changes still need an ordered, observable, and reversible path from the tagged baseline to the final local schema.

Business impact: replaying scripts out of order, dropping the database, or restoring known duplicate rows would turn a small release failure into data loss or renewed corruption.

Acceptance criteria: every migration has a ledger version, expected-version preflight, failure-on-error behavior, and a paired rollback; a baseline copy upgrades in place; rollback preserves quarantine and uniqueness; the same database upgrades again; a backup verifies; and a five-minute smoke procedure proves final invariants.

Technical approach: migration 006 validates all prior release objects before recording the final version and installs `usp_Triage_ReleaseSmokeTest`. Rollbacks run only from their exact version. They restore earlier procedure contracts where necessary, but deliberately retain safe additive indexes and quarantined rows. `scripts/Test-Rel139.ps1` creates one explicitly named disposable database, records its database ID, performs both forward passes and every rollback, and removes only that database and its temporary backup.

Risks: schema locks briefly block local callers, so the application is stopped during migration. A database rollback can require a matching application rollback. Retained safety objects mean rollback is compatibility-oriented rather than an attempt to recreate the defective baseline.

Test evidence: `.local/test-results/REL-139-release-verification.txt` records the main smoke, baseline fixture, in-place version 1→6 upgrade, `BACKUP` plus `RESTORE VERIFYONLY`, version 6→1 rollback, preserved archive/invariants, and second version 1→6 upgrade. The report is local runtime evidence and intentionally untracked.

Deployment notes: follow `docs/deployment-runbook.md`. No migration or rollback drops or recreates the main `Triage` database. Only the explicit reset script may recreate local demo state.
