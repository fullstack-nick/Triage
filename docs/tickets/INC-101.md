# INC-101 — one logical review per assignment

Problem: first-save requests can race and create duplicate review rows.

Business impact: a reviewer may see inconsistent saved content, and later updates can affect multiple physical rows.

Acceptance criteria: deterministic cleanup, archive conservation, database uniqueness, one row under 20 concurrent saves, stable draft ID, idempotent identical final retry, and rejection of changed post-final content.

Technical approach: quarantine surplus rows, create a unique assignment index, and serialize the atomic save/final/audit transaction on the owned assignment row.

Risks: cleanup must never lose data; index creation briefly locks the table; retry behavior must not create duplicate audit events.

Test evidence: `scripts/Test-Inc101.ps1` plus `database/tests/inc-101-review-uniqueness.sql`.

Deployment notes: apply migration 002 after a backup; retain `ReviewDuplicateArchive`; prefer an application rollback that keeps the invariant.
